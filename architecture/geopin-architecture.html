Design document · decided before implementation

GeoPin Architecture

A geotagging app: fetch pins, show them on a map or in a list, open one for its image and notes, add new ones. Four screens, two resources, and one dataset rendered two ways — that last property drives almost every decision below.

01

The one decision everything follows from

Name the kinds of state before writing a line of code. Most React Native spaghetti comes from treating all three as one thing.

KindExamplesOwnerLives in
Serverpins, pin detail, notes, image URLsthe server; we hold a cache that can go staleexternal store
Clientmap/list toggle, draft pin form, map region, filtersthe appuseState / useReducer, or useStoredState if it must persist
Navigationcurrent screen, route paramsReact NavigationReact Navigation — never mirrored

The failure this prevents: putting selectedPinId in a global store and in route params, then losing a day to why they disagree. Route params are the truth for “what am I looking at”. The store is the truth for “what is it”.

Arrows point inward, never outward. domain/ imports nothing from the app. store/ imports the repository interface, never an implementation. The UI never touches store/ internals — only hooks/.

That single rule is what makes the app testable in Node with no simulator, and it is the whole of Dependency Inversion in practice.

How this maps to SOLID

PrincipleWhere it shows up
Single responsibilityA screen renders. A hook subscribes. The store holds truth. A repository talks to the network. Four reasons to change, four places.

Dependency inversionThe store depends on the interface; App.tsx injects the implementation. The composition root is the only place that knows both.
03

The store primitive

Roughly forty lines, no dependencies. This is the entire state-management “framework”.

export const createStore = <S>(initial: S): Store<S> => {
  let state = initial;
  const listeners = new Set<() => void>();
  return {
    getState: () => state,
    setState: (updater) => {
      const next = updater(state);
      if (Object.is(next, state)) return;   // no-op writes don't notify
      state = next;
      listeners.forEach((l) => l());
    },
    subscribe: (listener) => {
      listeners.add(listener);
      return () => void listeners.delete(listener);
    },
  };
};

export const useSelector = <S, R>(store: Store<S>, selector: (s: S) => R): R =>
  useSyncExternalStore(store.subscribe, () => selector(store.getState()));

Entities are normalized as { byId: Record<string, T>, ids: string[] } — O(1) lookup by ID (exactly what an ID-only route param needs), one copy of each record, and a stable reference per entity that makes per-marker subscriptions possible.

04

Decision records

Each names the alternative it beat. A decision you can’t argue against isn’t a decision.

ADR-002Context for dependencies, external store for data

DecisionBoth, for different jobs. Context carries the store handles and repositories — built once, never changing, so it costs zero re-renders. useSyncExternalStore carries the data, so components subscribe to the slice they actually render.

WhyContext’s weakness is that useContext re-renders on any change to the provider value, with no way to add selector granularity. Its strength is injecting dependencies without prop-drilling. So: Context is for wiring, the store is for data.

Gave upThe familiarity of one usePins() context. The existing PinsContext demonstrates the cost directly: its value bundles pins with the mutators, so editing one title re-renders the map, the list, and every screen that only writes.

ADR-004useSyncExternalStore over Context for pin data

Why — specific to this app, not tasteThe map renders N markers at once. With Context, editing one pin’s title re-renders every marker plus the container, because they share one context value. At 50 pins that is a visible stutter on mid-range Android — on every edit, fetch, and add.

Cost~40 lines, plus one sharp edge: selectors must return referentially stable values or React throws “getSnapshot should be cached”. This is roughly how Zustand works internally, so the knowledge transfers.

ADR-007Suspense for code splitting only, not for data

DecisionYes for lazy, no for data — for now. Defer evaluating react-native-maps behind lazy + Suspense. Use the explicit AsyncState union for all data loading.

Why not for datause(promise) needs a referentially stable promise. One created during render is new every render and suspends forever. React’s supported sources are a Server Component passing a promise down — which RN doesn’t have — or a Suspense-enabled cache. Building that cache means building invalidation and staleness: i.e. writing TanStack Query.

The explicit union also gives us something Suspense doesn’t: a retry affordance. Suspense has no concept of “try again”.

NoteMetro ships one bundle, so lazy defers evaluation, not download — a startup win, not a payload win. Smaller benefit than on the web, and worth being precise about. This ADR is a deferral, not a rejection: ADR-011’s trigger flips it.

ADR-006Navigation carries IDs; screens resolve them

DecisionRoute params are primitives — { pinId: string }, never { pin: Pin }. Screens read the entity from the store and fetch on miss.

WhyReact Navigation serializes params for deep linking and state persistence; object params warn and break both. An object param is also a snapshot — edit the pin and the param still holds the old copy.

Consequence we acceptThe detail screen can mount with an empty store (deep link, restored state). So ensurePin(id) is required, not optional. This is the part most designs forget, and it breaks silently until QA.

ADR-009Map region lives in a ref, not state

DecisionCurrent region is a useRef, updated from onRegionChangeComplete. Never useState, never onRegionChange.

WhyonRegionChange fires continuously while panning — dozens of times a second. In state, that is a re-render per frame of the screen and every marker. onRegionChangeComplete fires once when the gesture settles; a ref holds it without rendering at all.

WeightThe single highest-impact performance decision in a map app, and invisible until you profile.

ADR-011Hand-rolled store now, TanStack Query at a named trigger

DecisionShip the 40-line store. Adopt @tanstack/react-query when any of these becomes true: two screens need the same resource at different freshness; we need background refetch or refetch-on-focus; we need offline cache persistence; or invalidation logic passes ~50 hand-written lines.

Why decide the trigger now“We’ll add a library when it gets complicated” is how you end up with 400 lines of hand-rolled cache nobody wants to delete. Naming the trigger in advance makes migration a planned step rather than an argument.

Gave upBatteries-included caching today. Accepted because the repository layer means the swap touches store/ and hooks/ only — and because every line of the hand-rolled version is explicable in an interview.

ADR-010Pin creation is pessimistic in v1

DecisionShow a saving state, wait for the server, then insert. No optimistic insert.

WhyA pin that appears on the map and then vanishes is genuinely confusing — a map is a spatial claim about the world, and a phantom marker reads as a bug. Creation is one fast request.

Gave upInstant-feeling adds. Cheap to reverse: insert with a temp ID, swap it on success, removeById on failure. One store action, no UI change — that is what normalization bought.

ADR-012Notes are a separate slice and repository

DecisionnotesStore keyed Record<pinId, EntitySlice<Note>>, with its own repository. Not nested inside Pin.

WhyNotes have their own lifecycle — fetched when a detail screen opens, not with the pin list. Nesting them would mean every note edit produces a new Pin object, re-rendering that pin’s marker on the map for no reason.

PrincipleSlice boundaries are re-render boundaries.

Also recorded, in brief: ADR-001 name the three kinds of state · ADR-003 normalize entities by ID · ADR-005 repository interfaces with injected implementations · ADR-008 map and list are one screen with a toggle.

05

The performance contract

Screens subscribe to IDs. Leaves subscribe to entities. PinsScreen reads ids; each PinMarker reads its own pin. The screen re-renders when the set changes; a marker re-renders when its pin changes. Nothing re-renders both.

  • Stable snapshots. useSyncExternalStore compares selector results with Object.is. A selector that builds a new array or object every call loops forever. Derived collections are computed once inside setState and stored.
  • Components take pinId, not pin. Passing the object puts the parent back in the subscription path and undoes ADR-004.
  • memo compares shallowly. One inline style={{ flex: 1 }} or data={pins.filter(...)} defeats it completely.
  • FlatList data is string[] of IDs, with stable renderItem and keyExtractor, plus getItemLayout for fixed-height rows.
  • Images need stable sources. source={{ uri }} is a new object every render → reload flicker. Use expo-image and give every image explicit dimensions.
  • Screens stay mounted. useEffect(..., []) never re-runs on back-navigation — anything refreshing on return uses useFocusEffect.
  • A Context value that changes is a bug here, not a tradeoff. Data belongs in the store.

Verify in order: count renders with useRenderCount → DevTools Profiler “Highlight updates” (panning should flash nothing; editing one pin should flash one marker) → only then reach for getItemLayout, a lower windowSize, or FlashList.

07

Build order

Ordered so every phase is verifiable before the next starts, and the untestable parts — map, GPS, camera — come last rather than blocking everything behind a simulator.

Domain and ports

Types, pure helpers, repository interfaces, HTTP and Fake implementations. No React, nothing to run.

Done when  fakePinRepository.listPins(signal) returns pins from a plain Node script.

The store

Store primitive, entity helpers, createPinsStore, the composition root, read hooks.

Done when  a test drives load → success → error → retry and asserts each transition. Still no UI.

List view

Memo’d PinRow taking a pinId, PinsScreen in list mode, async and error boundaries.

Checkpoint  mutate one pin from a debug button — exactly one row should log a render. Fixing this here is ten minutes; later it is a refactor.

Detail screen

Notes store, image, ensurePin fetch-on-miss.

Done when  launching directly onto a detail route with an empty store works. Test this deliberately — it is the path that breaks silently.

Map and toggle

Memo’d markers, region in a ref, persisted view mode, lazy around the map.

Done when  panning the map logs zero marker renders.

Add a pin

Draft in useReducer local to the screen; long-press to place; pessimistic save.

Done when  a new pin appears in both views with no refetch, and a failed save keeps the draft.

Performance pass

Now, not earlier, with 200+ seeded pins. Profile, then swap the fake repository for the HTTP one.

Done when  that swap is one line. If it is more, phase 0 was wrong.
