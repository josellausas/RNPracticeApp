# geopin

Expo SDK 55 / React Native 0.83 practice app: a map with pins, a Star Wars character
browser over SWAPI, and NFC tag register/read.

`ios/` and `android/` are generated by `npm run prebuild` and are gitignored — never edit
them. See [AGENTS.md](AGENTS.md) and [architecture/DECISIONS.md](architecture/DECISIONS.md)
(ADR-013).

## Everyday commands

```bash
npm run ios          # build + install + Metro, simulator by default
npm run android
npm run prebuild     # regenerate ios/ and android/ from app.config.ts
npm run typecheck    # tsc --noEmit
npm run lint
npm test
```

# Running NFC on a real device

**Pick-up notes.** No real tag has ever been read or written. The adapter is written,
unit-tested (103 tests) and compiles into the iOS app, but every NFC outcome so far has
come from the fake.

## Where the switch is

[`App.tsx`](App.tsx) — one flag:

```ts
const USE_REAL_NFC = true;   // true → react-native-nfc-manager, false → the fake
```

**Check its current value before you assume anything** — it was left `true` at the end of
the last session, which means the simulator shows "NFC unavailable" and the dev panel is
hidden. That is expected, not a bug.

When `true`, the provider gets no `control`, so `DevNfcPanel` (the yellow simulator
buttons) disappears automatically. Flip back to `false` to get it back.

## ⚠️ iOS on a device needs a PAID Apple Developer account

This is a hard blocker, not a warning to work around.

A free Personal Team cannot carry the `com.apple.developer.nfc.readersession.formats`
entitlement, which `ios/geopin/geopin.entitlements` now demands (written by the
`react-native-nfc-manager` config plugin). Xcode fails at **signing**, and the error talks
about provisioning profiles rather than NFC — which is what makes it confusing. At
runtime a Personal Team build would fail a session with *Sandbox restriction*.

### Step 1 — free check, no account needed

Do this first. It costs nothing and answers the one genuinely open question.

```bash
# App.tsx: USE_REAL_NFC = true
npm run ios          # simulator — no signing, entitlements not enforced
```

Open **Menu → NFC Read**. Expected: **"NFC unavailable"**.

That result proves the legacy native module loads and responds under RN 0.83's bridgeless
runtime (the compile only proved it *builds*), that `isSupported()` returns false cleanly,
and that the adapter's `unavailable` path renders. A crash, red box, or a spinner that
never resolves means a bridgeless problem — investigate that before spending $99.

### Step 2a — iOS, after enrolling ($99/yr)

1. Enroll in the Apple Developer Program. Activation takes a day or two.
2. At developer.apple.com, register an **explicit** App ID for `com.josellausas.geopin`
   — a wildcard App ID cannot hold the capability.
3. Enable **Near Field Communication Tag Reading** on that App ID.
4. Open `ios/geopin.xcworkspace` (the workspace, not the `.xcodeproj`), go to
   Signing & Capabilities, and set your Team. `DEVELOPMENT_TEAM` is currently unset.
   Let Xcode regenerate the provisioning profile.
5. Run:
   ```bash
   npx expo run:ios --device
   ```

If Xcode reports the profile doesn't include the NFC entitlement, step 2 or 3 was skipped
or the profile is stale — regenerate it.

### Step 2b — Android, free and works today

Android needs no paid account and no entitlement, only `android.permission.NFC`, which the
config plugin already added. Same adapter, same port.

```bash
npx expo run:android --device
```

If you have an NFC-capable Android phone, this is the cheapest way to validate the real
code path end to end.

### Step 3 — what to actually test with a tag

Tags: NTAG 215. The payload written is the character's SWAPI URL, e.g.
`https://swapi.info/api/people/1`, as an NDEF **URI** record (~28 bytes against the tag's
~504, so capacity is a non-issue).

1. **Menu → SW Characters → Register NFC** on a character. Hold a blank tag. Expect
   "Tag registered" and the tag's hardware UID, then **Done** returns to the list.
2. **Menu → NFC Read.** Hold the same tag. Expect "Found: *name*" and **See Profile**.
3. Edge cases worth provoking: dismiss the iOS sheet (→ "Cancelled"), scan a blank tag
   (→ "Blank tag", distinct from "Unknown tag"), scan a tag written by another app
   (→ "Unknown tag"), press back mid-scan (→ session aborts).

## Running from Xcode directly

Works, but Xcode does **not** start Metro. Either run `npx expo start --dev-client` in a
second terminal first, or just use `npx expo run:ios --device`, which does build, install,
and Metro in one step.

## NFC architecture, in one paragraph

Screens depend on a port ([`nfc/types.ts`](nfc/types.ts)) — three methods, and every
outcome is a union member rather than an exception. Adapters implement it:
[`fakeNfcReader`](nfc/adapters/fakeNfcReader.ts) (simulator + tests) and
[`nfcManagerReader`](nfc/adapters/nfcManagerReader.ts) (real). Both are wrapped in
[`guardReader`](nfc/guardReader.ts), which races every call against the abort signal and a
watchdog so a lost native callback can't strand the UI, converts rejections into `error`
outcomes, and serializes sessions. A Swift module would be a third adapter and would need
no screen changes.

## Known open items

- **Android error mapping is provisional.** `buildNfcExceptionAndroid` in nfc-manager only
  classifies the string `'cancelled'`; everything else arrives as a bare error. The
  adapter's Android branch matches on inferred message patterns — marked `PROVISIONAL` in
  the source. Capture real errors from a device and correct them.
- **Sessions are mount-scoped, not focus-scoped.** Both NFC screens use `useEffect`, so a
  screen that is obscured but still mounted keeps its session open — on iOS that's a live
  system sheet over a new screen. Consider `useFocusEffect`. There's a test in
  `screens/__tests__/nfcBackNavigation.test.tsx` that currently asserts the present
  behaviour deliberately.
- **`api/__tests__/swapi.test.ts` is committed fully commented out**, so `npm test` exits
  non-zero even though all 103 tests pass. Delete the file or uncomment it.
- `isAvailable()` on the port is currently unused by any screen — all unavailability
  detection happens inside `scan`/`write`.
